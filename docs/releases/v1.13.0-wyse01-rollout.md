## Proposed maintenance and bootstrap plan

Allow 20–30 minutes including recovery reserve after separate WYSE01 approval.
Require stable VNC, an available administrator, fresh baseline hashes/status,
no pending transaction/worker execution and adequate free space. Arrange a
current backup decision specifically for WYSE01; LOGIN01's prior same-host
backup exception is not a blanket approval for other machines.

The old updater has no shared kernel lock. A direct combined update can race
its scheduled recovery. Conversely, running the new 1.13.0 CLI to install a
1.13.0 package fails its correct equal-version check. Do not work around this
by relabeling packages, changing versions, disabling recovery or enabling a
worker. Use a controlled two-phase bootstrap, keeping the verified old engine
as part of this single maintenance operation:

1. Recheck and record live versions, client certificate/mode, networking,
   LightDM/VNC/status states, installed public key and transaction absence.
   Upload only the two signed packages and public key to a fresh root-only
   maintenance directory; verify ZIP/payload hashes and the Stable fingerprint.
2. Take a new mode-0700 full client recovery snapshot on WYSE01, preserving exact
   old binaries, client configuration, token, device CA/current/previous bundle,
   status units/drop-ins, VNC/LightDM/PAM configuration, update-state and original
   timer states. Keep secrets on the client. Hash/verify every saved file.
   Retain an executable copy of the old updater with the exact observed hash
   in this protected directory; it must not be overwritten during bootstrap.
3. Confirm `flock` is available and uses the same kernel lock file as the new
   updater: `/var/lib/stumpfworks-badge/update-transaction.json.lock`. Stop the
   status timer and let any active status service finish. Do not restart
   LightDM, NetworkManager or VNC. Do not perform a network outage test here.
4. **Phase A:** with that external exclusive nonblocking `flock` held, run the
   saved old updater's normal signed `--install` on the updater-only package,
   using fresh distinct stage and rollback directories. Select the Stable
   public key explicitly. This package contains no status component, so its
   normal health callback does not start the status service or require the
   paused timer. Require success, cleared transaction marker and the exact
   new updater hash/version. Preserve Phase A's component-bound rollback.
5. Resume the originally active status timer and confirm a normal certificate-
   authenticated report. The now-installed 1.13.0 recovery pre-hook recognizes
   the shared kernel lock. Before Phase B require status still exactly 1.12.2
   and updater exactly the signed 1.13.0 payload; stop on any drift.
6. **Phase B:** use the same saved, hash-verified old engine under the same
   external `flock` to install the two-component package with its own fresh
   stage/rollback directories. The legacy engine still verifies the signed
   1.13.0 manifest; the updater replacement is the identical Phase A payload,
   while status advances from 1.12.2. The external lock prevents the new status
   pre-hook from mistaking this live legacy-engine transaction for a crash.
   Keep the status timer active for the mandatory post-install report/health
   gate. Never reuse this legacy-engine recipe for another release or baseline.
7. Use the installed new updater's `--accept` against Phase B's package and
   rollback; separately verify Phase A's updater-only rollback/package binding.
   Acceptance supports an already-installed equal release and does not install
   it again. Require exact installed hashes, both complete rollback manifests,
   no pending transaction, fresh successful mTLS status and healthy original
   services. Confirm VNC stability independently; non-greeter package health
   alone does not prove it.
8. Confirm LOGIN01 receives status version 1.13.0, unchanged certificate-required
   mode, healthy readiness fields and the bounded success/rollback result.
   Confirm normal AD username/password login with the user. No LightDM restart,
   forced enrollment/renewal, token fallback, client-mode change, worker startup,
   catalog change or server target-version change is part of this window.

Any phase failure stops the sequence. Treat the two phases as one supervised
bootstrap; do not automate them as two server jobs. A job cannot bootstrap a
worker that is not installed. The service orchestration above remains subject
to real maintenance acceptance; it was not executed during preparation.

## Rollback and stop conditions

Installation/health failure invokes the existing verified automatic rollback.
Phase A failure must leave the original updater and paused timer recoverable;
restore its recorded timer state before leaving the window. Phase B rollback
restores status 1.12.2 and the already-bootstrapped new updater. For a full
return to the original baseline, restore the two phase snapshots in reverse
order using the validated fixed-target recovery mechanism, then verify the
original status/updater hashes and saved service states. Keep the full client
snapshot as an additional exact recovery source; never delete older rollbacks.

Do not invent a broad manual restore CLI or supply arbitrary recovery targets.
If interrupted, pause competing timers, inspect the durable transaction marker,
verify its release/component binding and all saved hashes, and use the existing
pending recovery path under the original maintenance authority. Do not clear a
marker or journal merely to make a health check pass. Preserve evidence if
recovery cannot validate the snapshot.

Stop for unstable VNC, baseline drift, signature/hash/key mismatch, missing
backup, pending transaction, lock contention, failed status/AD/LightDM health
or loss of access. Resolve these under explicit maintenance scope; no recovery
shortcut may alter MOBILE01 or downgrade WYSE01's authentication mode.

Preparation is complete; production rollout is held pending stable VNC and a
separate WYSE01 maintenance authorization. MOBILE01 remains excluded.
