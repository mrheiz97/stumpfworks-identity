# LOGIN01 v1.13.0 rollout preparation

Prepared 2026-11-01. **Read-only preflight completed; maintenance is not
authorized or started.** No candidate was copied to LOGIN01, no backup was
created there, no migration/service/configuration change was made. WYSE01 and
MOBILE01 are excluded, including client binaries, services, modes and updates.

## Observed baseline

LOGIN01 runs v1.12.2 with PostgreSQL 17.11 and migrations 1–6. Migration 7 and
`client_update_jobs` are absent. Identity, PostgreSQL and the daily maintenance
timer are active; Identity has no restarts or warning entries since the last
recorded maintenance. Time is synchronized; about 6.6 GiB is free.

All six public routes return HTTP 200: health, discovery, JWKS, login,
self-service and emergency login. Go 1.26.10 and OpenSSL verified the chain
and DNS identity with the existing CA, without insecure flags. Python's
default stricter X509 profile rejects the existing root CA because it lacks
KeyUsage; record this existing compatibility issue separately. It is not a
reason to disable TLS checks or rotate a CA in this server rollout.

The existing LDAP read check reports seven active users. It is not a new
interactive administrator login or a test of the candidate on production.
Metrics confirm v1.12.2/PostgreSQL, one fresh healthy client, one disabled
client and maintenance mode off. Port 8444 is listening; 8445 is closed.
WYSE01's existing certificate-required status reports are fresh and all four
readiness fields are `ok`; MOBILE01 remains disabled/token-only. No client was
contacted or changed. There are no pending credentials or usable enrollment
tokens at this observation time. Recheck these time-sensitive facts at entry.

The latest existing custom dump is `identity-20261101T074327Z.dump`, mode 0600
inside a root-only directory; `pg_restore --list` succeeds. This verifies its
archive catalog, **not** a production-data restore rehearsal. The existing
historical rollback manifest also verifies from its `files/` directory. Neither
replaces a fresh stopped recovery point for this change. Availability of a
current independent/off-guest backup has not been established by this preflight.

Runtime and backup roles have no superuser/database/role-creation or schema
CREATE rights. The migrator has schema CREATE; its default table privileges
grant runtime SELECT/INSERT/UPDATE/DELETE and backup SELECT on newly created
tables. Keep these identities separate; do not grant runtime DDL to deploy.
Runtime, migrator and backup connection settings all specify `sslmode=verify-full`;
the observed backup-role connection negotiated TLS 1.3.

## Proposed maintenance window — execute only after separate approval

Allow 20–30 minutes including verification and recovery reserve; this is a
planning estimate, not measured downtime. Stopping Identity interrupts new
server-backed logins, OIDC operations and client status delivery. Existing
client services remain running. Arrange administrator availability for the
interactive acceptance before entering the window.

1. Repeat baseline checks; confirm exact tag/hashes, fresh client status,
   no pending enrollment/renewal, healthy services, free space and independent
   backup availability. Record UTC times, timer enabled/active state and the
   current schema. Stop if any baseline differs or an enrollment is underway.
2. Under the new approval, stage only the three candidates in a new root-only
   server directory; check hashes there before touching installed paths. Check
   candidate version and perform the database-free directory check with the
   same effective environment as the service. Do not start a second server.
3. Enter the existing monitoring maintenance mechanism, preserving its former
   state. Pause the daily maintenance timer for this bounded window and wait
   for any already-running backup to finish. Record states for restoration.
4. Stop only Identity and confirm it is stopped and database writers belonging
   to Identity have drained. Keep PostgreSQL running. This establishes the
   no-application-write recovery boundary. Recheck that no other writer exists.
5. Create a **new** mode-0700 rollback directory with restrictive umask. Preserve
   exact installed server/admin/migrator binaries, all Identity configuration
   and credentials/CA/signing files, full unit/drop-in configuration, maintenance
   scripts/units, PostgreSQL configuration/role/grant recovery information and
   the protected migrator credential reference. Keep secrets on the server.
   Record owners/modes and SHA-256; verify the complete file manifest.
6. Using the existing TLS-verified read-only backup identity, create a fresh
   custom dump while Identity is stopped. Include it in the recovery manifest
   and verify its catalog with `pg_restore --list`. Preserve globals/ownership
   needed for restoration separately in protected storage. Do not replace any
   historical backup. If the recovery set is incomplete, restart the old server
   and restore original timer/maintenance state; do not migrate.
7. Bind `IDENTITY_RELEASE_STAGE` to the verified staging directory and
   `IDENTITY_MIGRATION_URL_FILE` to the existing protected migrator URL file.
   Run the staged v1.13.0 executable, not the old installed migrator:

   ```sh
   "$IDENTITY_RELEASE_STAGE/identity-db-migrate" --postgres-url-file "$IDENTITY_MIGRATION_URL_FILE" \
     --confirm create-empty-identity-schema schema
   ```

   This command's existing confirmation label also covers forward migrations
   on the established database; it does not imply dropping or replacing it.
   Require `schema=ready`, versions 1–7 with expected checksums, the new table
   empty and runtime/backup grants present. No import or SQL bypass is needed.
8. While stopped, atomically replace each of the three binaries with the
   verified candidates, preserving original ownership/mode. Configuration and
   units stay unchanged. Verify installed hashes and version, then start only
   Identity. Record the restart time; this is the point after which normal
   production writes may resume immediately, including status reports.
9. Run the acceptance checks below. On failure keep the maintenance boundary
   active, stop Identity and follow the applicable rollback branch. On success,
   run the existing backup maintenance path, verify its fresh dump and marker,
   restore the recorded timer and monitoring state, and verify no warnings.
   Retain the new recovery directory through acceptance and normal retention.

## Acceptance and abort criteria

- Installed hashes/version exactly match v1.13.0; Identity and PostgreSQL are
  healthy, schema is 7 and runtime still lacks DDL privileges.
- All six public routes return 200 with full TLS verification; metrics report
  v1.13.0/PostgreSQL; 8444 remains active and 8445 closed. No new warnings.
- The next naturally scheduled WYSE01 report succeeds under the existing
  certificate-required mode, and its readiness fields remain healthy. Verify
  this from LOGIN01; do not trigger a client command or change its mode/token.
  MOBILE01 remains disabled and no client update job is created.
- Administrator performs a normal AD login and checks dashboard, audit,
  OIDC administration and the read-only client certificate page. Verify the
  existing OIDC application path within the agreed acceptance; do not rotate
  secrets or revoke sessions as a smoke test.
- New certificate page/API authorization and absence of secret fields are
  confirmed with the authorized existing role. Update catalog remains empty,
  jobs remain empty and no worker/timer activation occurs.
- Stop acceptance for failed startup/migration, TLS/LDAP/OIDC regression,
  unexpected client authentication rejection, lost privileges, unhealthy backup,
  new error journal entries or candidate/configuration drift. Do not improvise
  a CA rotation, mode downgrade, direct SQL fix or client rollout.

## Rollback branches and write-loss boundary

**Before new application writes:** keep Identity stopped. If migration did not
commit, verify schema state and restore the original binaries/configuration.
If migration 7 committed and full rollback is selected, preserve the failed
state and restore the fresh stopped schema-6 database snapshot together with
its exact matching binaries/configuration. Restore into a protected alternate
database first and verify before selecting it; preserve the failed database.
Keep existing role ownership/grants and TLS behavior. There is no automatic
down-migration, table drop or migration-ledger deletion.

**After the new server has accepted writes:** stop Identity again and preserve
the current database plus audit/recovery evidence before any restore. Restoring
the pre-window dump would discard subsequent status, login/audit, credential
or other application writes. A complete restore therefore needs an explicit
data-loss/reconciliation decision at that time. Never silently discard these
writes or claim the old binary alone reverses the schema change. Retaining
schema 7 while reverting binaries is a separate compatibility decision, not
the default complete rollback promised by this plan.

Restart the chosen consistent previous set, then verify v1.12.2 hashes, schema,
six HTTPS routes, LDAP/administrator/OIDC access, natural WYSE01 status, unchanged
MOBILE01 state and backup health. Restore recorded timer/monitoring state only
after recovery checks. Do not alter either client as a recovery shortcut.

The local rebuilt v1.12.2 recovery set and certificate-only reverse-patch
rehearsal remain useful software evidence, but do not contain current production
configuration/database and cannot replace the new stopped snapshot.
