# v1.2 client management

The first v1.2 increment adds a deliberately narrow, server-side foundation for centrally visible client health. It does not change the badge, PIN, PAM, PKINIT, Kerberos, or CIFS paths and is not deployed automatically.

## Security model

- An administrator provisions a client locally on LOGIN01 with `sw-badge-server -config /etc/stumpfworks-badge/config.yaml -register-client <client-id>`.
- The command prints a cryptographically random bearer token exactly once. Only its SHA-256 hash is stored in SQLite.
- A client may submit only its own bounded status document to `POST /api/v1/client/status` over the existing verified TLS connection.
- `GET /api/v1/clients` remains behind the existing administrator session guard.
- Status values are limited to `unknown`, `ok`, `degraded`, or `unavailable`. Version and client ID lengths are bounded; unknown JSON fields and bodies over 4 KiB are rejected.
- Status reports contain no usernames, network addresses, SSIDs, badge data, PINs, tokens, private keys, logs, or free-form diagnostic text.

## Status document

```json
{
  "client_id": "wyse01-greeter",
  "version": "1.2.0-dev",
  "network_status": "ok",
  "ad_status": "ok",
  "camera_status": "ok",
  "kerberos_status": "unknown",
  "update": {
    "version": "1.2.0",
    "status": "success",
    "updated_at": "2026-08-27T20:50:48Z",
    "rollback_available": true
  }
}
```

The `update` object is optional for backward compatibility. It contains only the last updater outcome and never includes paths, package contents, command output or credentials.

## Client collector

`sw-badge-client-status` is a short-lived process started by `swbadge-client-status.timer`. It reports once and exits. The collector checks only:

- whether a non-loopback interface is up and has a non-link-local address;
- whether `wbinfo -t` confirms the existing Winbind trust;
- whether a `/dev/video*` device exists;
- whether `kinit` and the PKINIT plugin are installed.

It does not enumerate or transmit interface names, addresses, SSIDs, AD users, logged-in users, Kerberos principals, logs, or command output. HTTPS is mandatory and the configured Homelab CA remains in use.

The guided client installer accepts the one-time provisioned token, stores it as root-only mode `0600`, installs the collector and enables its timer. It performs one immediate status submission but does not restart LightDM unless separately confirmed.

The protected LOGIN01 system-status page renders all registered clients and labels reports older than three minutes as stale. Fresh reports are healthy only when every bounded readiness check is `ok`; otherwise they are marked for attention. Clients that have not submitted a report are shown separately. The reported semantic version is compared with the configured managed-client target and displayed as current, update available, client newer, or unknown. LOGIN01's own build version is displayed separately. The optional last-update outcome shows its target version, bounded result, timestamp and rollback availability. This is informational and does not download or install software.

The target is configured with `updates.client_target_version` or the `SWBADGE_CLIENT_TARGET_VERSION` environment variable. If neither is set, the running server build remains the backward-compatible fallback. Invalid semantic versions stop server startup instead of silently producing misleading update status.

The guided LOGIN01 installer asks for this managed target separately from the server build version. The guided Linux-client installer also installs the guarded updater and only the selected public Ed25519 verification key; private release keys remain outside both LOGIN01 and all clients.

## Credential lifecycle

Client status credentials are managed locally on LOGIN01 so secrets never pass through browser URLs, forms, audit pages, or application logs:

```bash
sw-badge-server -config /etc/stumpfworks-badge/config.yaml -rotate-client-token wyse01-greeter
sw-badge-server -config /etc/stumpfworks-badge/config.yaml -disable-client wyse01-greeter
sw-badge-server -config /etc/stumpfworks-badge/config.yaml -enable-client wyse01-greeter
```

Rotation invalidates the old token immediately and prints the replacement exactly once. Disabling rejects status reports even when the correct token is supplied; requests with an incorrect token still receive the generic credential error and cannot discover whether a client is disabled. Re-enabling does not rotate the token.

At this stage, disabling applies only to the status-reporting credential. Badge/PIN authentication is deliberately unchanged to avoid locking out an existing production client before an explicit enforcement migration and rollback have been designed.

The staged successor design is documented in
[`client-device-authentication.md`](client-device-authentication.md). It keeps
this bearer credential as a per-client rollback path while device certificates
are introduced first for status reporting. It does not authorize a production
certificate rollout or change Badge/PIN and PKINIT implicitly.

## Privacy-limited diagnostics

`sw-badge-client-diagnostics` creates a mode `0600` ZIP containing `diagnostics.json` and a privacy notice. The report contains the client ID, software version, OS/architecture, bounded readiness states, selected systemd states and booleans confirming HTTPS, readable CA material and a securely permissioned token file. It reads no token or certificate contents and includes no addresses, SSIDs, usernames, logs or Kerberos principals. The guided installer creates one archive automatically after its first successful status report.
